# 文档标准化规范（Documentation Standards）

> 本文档定义 AI Edge Gallery for API Use 项目所有文档的编写、命名、结构与维护规范。
> 适用于仓库内所有 Markdown 文档、Kotlin KDoc 注释、API 参考与发布说明。

## 1. 文档分层

写文档前必须先判断受众，不同层级的文档不得混写。文档分四层：

| 层级 | 用途 | 存放位置 | 示例 |
| :--- | :--- | :--- | :--- |
| 内部真源 | 架构决策、Owner 归属、验收门禁、治理记录、阶段计划、漂移控制 | `docs/` | 本文件 |
| 外部用户文档 | 使用、部署、配置、公开 API、集成、运维、排障 | 仓库根 README | `README.md` |
| 发布说明 | 版本变更、行为变化、迁移指引 | Release notes | 发版条目 |
| 一次性记录 | 复盘、审计结论、过时会话 | 归档目录或标注非当前 | `archive/`（按需创建） |

> 当前仓库尚未建立「文档索引」「ADR」「Owner Map」等设施；`docs/user/` 暂未启用。
> 后续若引入，须在本文件维护清单中登记并补充引用。

### 1.1 禁止事项

- 禁止把审计结论、内部治理、一次性复盘混入用户文档。
- 同一变更同时影响用户行为与内部机制时，必须分别写入对应层级，不得只写一边。
- 新增真源文档须在 `docs/` 下保持独立文件，并在引入文档索引设施后登记；失效、被吸收
  或一次性的文档必须归档或标注「非当前」，禁止留在主目录误导后续维护者。

## 2. 命名约定

| 对象 | 约定 |
| :--- | :--- |
| 文件名 | `SCREAMING_SNAKE_CASE.md`（如 `DOCUMENTATION_STANDARDS.md`、`RELEASE_PROCESS.md`） |
| 用户可见标题 | 中文，简洁描述用途，不超过 12 字 |
| 章节标题 | 中文，层级从 `#` 开始递增，禁止跳级 |
| 链接 | 仓库内相对路径；指向 GitHub 外部资源用完整 URL |
| 术语 | 首次出现用中文全称（括号注明英文/缩写），如「魔搭社区（ModelScope）」 |

## 3. 结构模板

每个文档应包含以下区块（按需裁剪，顺序固定）：

```markdown
# 标题

> 一段话说明本文档回答什么问题、给谁看。

## 背景 / 背景与动机
## 说明 / 规范正文
## 示例（如有）
## 维护
- 本文档由谁维护
- 何时需要更新
- 与之同步的代码/文档
```

### 3.1 README 模板（仓库根）

```markdown
# 项目名

> 一句话定位 + 核心能力摘要。

## 功能特性
## 快速开始 / 使用说明
## 配置项
## 致谢 / Acknowledgments
## 许可证 / License
```

## 4. 语言约定

- 用户可见文档用简体中文；代码标识符、路径、命令、URL 用英文原样书写。
- 避免中英混排长句；技术名词首次出现时括号注明原文。
- 命令、代码块必须标注语言类型（```kotlin、```bash、```json）。
- 禁止用「应该」「可能」等模糊词表述必须行为；规范条款用「必须 / 不得 / 建议」明确语气。

## 5. 代码内文档（KDoc / 注释）

- 公共 API 必须写 KDoc，说明用途、参数、返回与异常。
- 实现注释解释「为什么」，不解释「是什么」（代码本身应自解释）。
- 注释与被注释代码使用相同语言：项目内代码注释以英文为主（沿用上游 Google 惯例）；
  新增面向用户的功能说明文案（UI 字符串、提示）用中文。
- 禁止留 TODO 不带上下文；TODO 必须标注责任人或 issue 链接。

## 6. 维护与生命周期

- 文档必须与代码同步：修改代码、接口、配置、架构边界、用户行为或产品语义后，
  必须同步更新受影响文档，并在同一提交中完成。
- 每次发版前检查：README 功能清单、CHANGELOG 条目、文档索引、失效文档归档是否齐备。
- 文档审查纳入代码审查流程：任何 diff 若改动行为，必须同时审查文档是否同步。

## 7. 审查清单

提交文档前逐项核对：

- [ ] 受众分层正确（内部 / 用户 / 发布 / 归档）
- [ ] 命名与结构符合本规范
- [ ] 无过期信息残留、无重复文档、无未归档的旧文档
- [ ] 代码示例可运行，命令可执行，路径准确
- [ ] 与代码行为一致（配置项、API、默认值逐一核对）
- [ ] 许可证 / 致谢信息完整
